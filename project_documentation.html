Plateforme de contrôle d'accès Zero-Trust

ZT_project

Une passerelle API où chaque requête est authentifiée, scorée par un modèle de détection d'anomalie, puis autorisée par un moteur de politique qui combine RBAC, score de risque ML et règles indépendantes du score — avec un journal de décisions à chaîne de hash inviolable. Ce document décrit l'architecture réelle du système et renvoie, section par section, vers le code et l'état vérifié en direct qui le prouvent.

7 composants 21 routes API documentées (/docs) 16 dimensions du vecteur de comportement 76 388 décisions auditées, chaîne intacte

01 Vue d'ensemble

Le principe Zero-Trust appliqué ici : un jeton valide et un rôle autorisé ne suffisent jamais à eux seuls. Trois couches de décision, indépendantes les unes des autres, doivent toutes être franchies.

RBAC toujours

Rôle → action autorisée. Vit dans OPA, pas dans le code Python — policies/authz/rbac.rego.

Score ML si actif

Isolation Forest, comportement récent vs seuil calibré (percentile p98). Absent en bootstrap.

Règles indépendantes toujours

IPs distinctes, énumération de ressources, actions sensibles — bypass délibéré du score quand il est trop dilué pour réagir seul.

Ce choix architectural — score ML jamais seul juge — est la réponse directe à une limite mesurée en direct sur ce projet : un signal fort sur une seule dimension parmi 16 se dilue trop dans un Isolation Forest pour faire bouger le score de façon fiable (AUC holdout ≈0,69–0,70 sur les scénarios les plus nets). La section Cycle de vie du modèle détaille pourquoi, avec des chiffres réels de ce système.

02 Architecture & composants

Sept composants, quatre natures différentes. C'est la source d'une confusion fréquente : seul le premier expose une API REST — les trois services ML/comportemental n'ont aucune route HTTP, par conception, pas par oubli.

api-gatewayREST

FastAPI. Seul point d'entrée public (dmz_net + internal_net). Authentifie, score, autorise, audite chaque requête. Swagger complet sur /docs.

policies/ (OPA)bundle Rego

RBAC + adaptive access + MFA, combinés dans authz/decision.rego. Appelé par le gateway sur chaque requête authentifiée, via mTLS.

isolation-forestREST interne

A un vrai FastAPI (/score, /health) — mais expose: seul dans docker-compose, jamais publié sur l'hôte, et exige un certificat client mTLS. Invisible depuis un navigateur.

ml-trainerjob batch

Aucun serveur. docker compose run --rm ml-trainer — entraîne un Isolation Forest, s'arrête. Zéro route HTTP dans son code.

canary-validatorjob batch

Idem — compare un candidat au modèle en production sur du trafic réel, écrit dans canary_validation_log, s'arrête.

behavioral-detectordaemon

Process long-running sans serveur HTTP — une boucle (scan; sleep(60)) sur les mêmes fenêtres Redis que le vecteur ML, pour les patterns que le score dilue trop.

dashboard (Argus)SPA React

Ne parle qu'au gateway, depuis le navigateur — jamais aux autres services directement. Sur monitoring_net seul.

Pourquoi ça compte

Demander "où sont les endpoints de canary-validator" revient à demander où sont les endpoints d'un script cron — la question part d'une hypothèse (tout composant expose une API) qui ne tient pas ici. Le Swagger du gateway est le seul qui puisse exister dans ce projet ; les trois autres composants ML se lisent dans leur code source, pas dans un navigateur.

03 Pipeline de décision

Le mécanisme central : le score ML et les règles indépendantes sont calculés en parallèle, sur les mêmes 16 dimensions de comportement, et convergent dans OPA — jamais l'un à la place de l'autre.

Décisions possibles

  • ALLOW — la requête atteint le handler.
  • STEP_UP — 401, un TOTP frais est exigé (POST /mfa/challenge/verify).
  • DENY — 403 {"detail": "access denied"}. Le motif exact (policy_name) n'existe que dans le journal, jamais dans la réponse au client.

06 Journal d'audit inviolable

Chaque ligne de opa_decision_log est chaînée par SHA-256 à la précédente (app/core/audit_hash_chain.py) — modifier un seul champ, sur une seule ligne, casse la chaîne à partir de ce point. 

poetry run python scripts/verify_audit_integrity.py
> OK: 76388 rows verified, chain intact from genesis to tail
# ou, si une ligne a été altérée :
> AUDIT TRAIL INTEGRITY BROKEN at opa_decision_log.id=60962:
>   row_hash does not match the recomputed hash

Script en lecture seule — sûr à lancer à tout moment, y compris pendant une démo, sans rien modifier.

07 Vecteur de features (16 dimensions)

Construit par le Gateway à chaque requête authentifiée, depuis des compteurs Redis à fenêtre glissante de 5 minutes — avant que la requête courante ne soit elle-même enregistrée, pour qu'elle ne s'influence jamais elle-même.

#DimensionFenêtre
0–4Méthode HTTP (one-hot)instantané
5Nombre de requêtes1 min
6 / 7Routes / ressources distinctes5 min
8 / 9Intervalle inter-requêtes (moy./écart-type)5 min
10Méthodes distinctes5 min
11Ratio lecture/écriture5 min
12Nombre de DENY récents5 min
13IPs distinctes5 min
14Échecs d'authentification (par IP)5 min
15Latence de la requêteinstantané

Score final : score_samples() (Isolation Forest, non supervisé) → sigmoïde bornée [0,1] → rang percentile dans un batch de calibration (canary-validator) — parce que la sigmoïde brute se regroupe trop fort sur ce trafic réel (~0,55–0,66) pour séparer normal et anormal.

08 Cycle de vie du modèle

Aucun modèle ne devient actif sans calibration et validation humaine — même le modèle ML lui-même suit une gouvernance explicite, pas juste les décisions qu'il produit.

11 Limites assumées

Documentées volontairement, pas cachées.

  • Population d'entraînement — ml_training_samples est intégralement produit par les comptes de démo seedés du projet, pas par de vrais utilisateurs externes ; les seuils empiriques sont valides dans cet environnement, pas garantis transférables à une population réelle.
  • Modèle jeune — deux cycles d'entraînement/calibration seulement, AUC holdout ≈0,69–0,70 sur les scénarios les plus nets. C'est précisément pour ça que ce score n'est jamais le seul juge (voir MFA adaptatif).
  • Vault en mode dev — stockage en mémoire, régénéré à chaque redémarrage de la stack ; adapté à ce projet, pas à une mise en production telle quelle.
  • Portée mTLS volontairement restreinte — Gateway↔OPA et Gateway↔Isolation Forest uniquement ; Vault lui-même reste en HTTP simple.
